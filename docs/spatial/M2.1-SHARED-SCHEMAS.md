# M2.1 — Shared Spatial Schemas

**Статус:** verified  
**Scope:** typed transport boundary for Spatial canonical summaries  
**Owner:** `web/operator-dashboard/src/spatial/contracts/`

M2.1 introduces the first canonical data boundary after Prototype A. The
renderer remains presentation-only: payloads are parsed before they can enter
query/store code, and no contract module imports Three.js, React Three Fiber or
Spatial UI components.

## Contract surface

`@/spatial/contracts` exports Zod schemas and types for:

- `spatial.entity.v1` — discriminated `agent`, `endpoint`, `service`,
  `session`, `artifact`, and `attention` summaries;
- `spatial.relation.v1` — typed semantic relationship between canonical refs;
- `spatial.node-status.v1` — authoritative Node state with component evidence;
- shared IDs, non-negative revisions, UTC timestamps, availability and
  freshness states.

Wire fields use the Node-facing `snake_case` contract. Known fields are
normalized at the boundary; unknown additive fields are accepted for a
compatible version and stripped before the parsed value is returned. This
keeps forward-compatible responses from carrying arbitrary payloads into a
store.

## Freshness and diagnostics

`normalizeSpatialFreshness` is the single freshness policy. It computes age from
the normalized `observed_at` timestamp and changes only an expired `FRESH`
record to `STALE`. `UNKNOWN`, `PARTIAL`, and `UNAVAILABLE` are explicit states
and are never upgraded by the browser.

`parseSpatialContract` returns a discriminated result. Malformed payloads are
reported as `MALFORMED_PAYLOAD`; a known contract family with a breaking
version is reported as `INCOMPATIBLE_SCHEMA_VERSION`. Diagnostics contain only
the contract, version, path, and Zod issue category — never raw payload values
or secret fields.

## Fixtures and acceptance

`src/spatial/contracts/fixtures.ts` provides good, stale, partial, malformed,
and incompatible-version fixtures shaped like existing Dashboard read-model
responses. `tests/unit/spatial-contracts.test.ts` proves:

| Acceptance ID | Criterion | Evidence |
| --- | --- | --- |
| `M2.1-AC-001` | Malformed payload is rejected before a store boundary | `parseSpatialRelation` unit test |
| `M2.1-AC-002` | Unknown additive fields do not break a compatible version | additive Agent fixture and parser test |
| `M2.1-AC-003` | Breaking schema versions produce an explicit incompatible state | `spatial.entity.v2` diagnostic test |
| `M2.1-AC-004` | Timestamp and freshness normalization is centralized | timestamp and TTL tests for `normalizeSpatialTimestamp` / `normalizeSpatialFreshness` |
| `M2.1-AC-005` | Entity classes and Node status use discriminated typed contracts | entity/status/relation schema export and fixture tests |

Run the slice with:

~~~text
pnpm --dir web/operator-dashboard test -- tests/unit/spatial-contracts.test.ts
pnpm --dir web/operator-dashboard typecheck
~~~

M2.2 will consume these contracts from domain clients and query-key factories;
M2.7 will be the first slice allowed to materialize them into the Spatial
renderer.

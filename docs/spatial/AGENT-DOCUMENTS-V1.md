# Agent documents v1 — сквозной слайс Pearl UI

Следующий слайс: [Interaction Seed, сохраняемый чат и Workspace-артефакты](INTERACTION-SEED-CHAT-V1.md).

Реализация [ADR-011](./ADR-011-agent-mediated-component-interface.md) для
`/operators/dashboard/react/spatial-calibration.html`. Это первый реальный
путь от запроса оператором формы до применения и проверки изменения через
MCP, а не завершение всей миграции Classic UI.

## Граница ответственности

```text
Текст / распознанная речь / изменение полей
  → существующий operator agent-channel
  → событие и durable inbox Primary Agent
  → MCP: aidn.ui.read / aidn.ui.present / aidn.ui.apply
  → canonical services ноды
  → проверенный документ / снимок сцены
  → зарегистрированные HTML-компоненты в Spatial frame
```

Браузер читает только канал агента и его публикации. Он не запрашивает
конфигурацию через fleet/endpoints/sessions API и не отправляет команды
изменения напрямую. Polling канала не запускает новый LLM-запрос; начальный
запрос сцены и явное обновление снимка являются сообщениями агенту.

Агент выбирает содержание и композицию документа, но не сочиняет значения
настроек и разрешения. HTML создаёт доверенный renderer из зарегистрированных
блоков. Произвольные HTML, JavaScript, внешние формы и `innerHTML` не допускаются.
Это намеренная реализация шаблонного документа, а не исполнение frontend-кода
модели. Classic dashboard остаётся отдельным существующим путём управления.

## MCP и контракт

`aidn.ui.read` принимает `request_id`, `kind` и точный `target_id`. Идентификатор
сначала разрешается доменными MCP-инструментами; при неоднозначности агент
уточняет цель. Источник содержит авторитетные поля, типы, доступность изменения,
ограничения, ревизию и время чтения. `source_id` привязан к поверхности и
текущему агенту. Снимок сцены не требуется копировать через текстовый ответ LLM.

`aidn.ui.present` принимает `request_id` и `document` либо `scene_source_id`:

```json
{
  "request_id": "request-example",
  "document": {
    "document_id": "endpoint-settings",
    "title": "Настройки endpoint",
    "blocks": [
      { "type": "text", "text": "Показываю только параметры запроса." },
      {
        "type": "fields",
        "title": "Генерация",
        "source_id": "source-from-mcp-read",
        "field_ids": ["parameter.temperature", "parameter.max_tokens"]
      }
    ]
  }
}
```

Идентификаторы в примере условные. Агент должен использовать значения из
реального события и ответа MCP. Повторная публикация с тем же `document_id`
обновляет тот же frame. Значения и `editable` подставляет сервер по `source_id`.

Общие поля: `text`, `number`, `integer`, `boolean`, `select`. Неизменяемые
значения отображаются текстом. Каждая группа содержит свой target/source;
форма передаёт `document_revision`, `source_revision`, `current` и `proposed`
только для изменённых полей. Сервер независимо проверяет эти исходные значения
и вычисляет diff. Нажатие «Применить через агента» само по себе ноду не меняет.

`aidn.ui.apply` получает только зарегистрированный `intent_id` и обычные
MCP-параметры `mode`, `request_id`, `idempotency_key`, `plan_hash`. Новые значения
нельзя подменить аргументами инструмента. Последовательность:

1. Планирование с проверкой актуальной ревизии endpoint и точного diff.
2. Обычная MCP-проверка scopes и `endpoint_write` approval policy.
3. Применение через существующие Endpoint services.
4. Повторное чтение с проверкой всех изменённых значений.
5. `APPLIED`, новая ревизия источника и обновление того же документа.

Автоматический read-back обновляет факты; следующая публикация агента может
уточнить пояснения. Без результата проверки UI не сообщает об успешном
сохранении. При требуемом подтверждении агент сообщает об этом, не утверждает
собственный план и не обходит policy другим инструментом. Отдельная форма
операторского подтверждения плана в этом слайсе ещё не добавлена.

## Реальное покрытие

| Источник | Просмотр | Изменение в этом слайсе |
|---|---|---|
| Provider | Безопасные метаданные, без секретов | Нет |
| Bundle | Идентификация и скалярные runtime-параметры | Нет; новая ревизия отдельным слайсом |
| Endpoint | Идентификация, local access, параметры запросов и размещения | Название и известные параметры запросов только неопубликованного endpoint; local access отдельно |
| Scene | Primary Agent, существующие endpoints/bundles/sessions | Только публикация нового снимка агентом |

Разрешённые параметры запросов ограничены известной provider policy:
`temperature`, `top_p`, `top_k`, `repeat_penalty`, `max_tokens`,
`frequency_penalty`, `presence_penalty`. Пределы проверяются на клиенте и
сервере. `consumer_editable` не подменяет права оператора. Тип числа не меняется,
если текущее значение, например temperature, равно целому нулю.

Изменение `local_agent_use` выполняется отдельно и не меняет publication
configuration hash. Настройки размещения модели и опубликованная конфигурация
не редактируются в обход ревизий. Вызов endpoint с записью аудио, медиа-ответы,
таблицы, revision workflows и полный каталог Classic forms остаются следующими
слайсами. Не все команды старого Presentation Planner уже подключены к этой
странице; новый renderer использует существующую Component Registry для
зарегистрированного `agent-document`.

## Состояния и хранение

- Читаемые данные подписаны как снимок с временем наблюдения, не как непрерывный
  live-поток. Отсутствующая конфигурация не заменяется демонстрационными объектами.
- Повторная доставка одного запроса идемпотентна. Изменённое содержание с тем же
  ID отклоняется. Повтор уже применённого intent возвращает проверенный результат.
- Устаревшие ревизии, подмена исходных значений, поля другой поверхности,
  неправильные типы и readonly-поля отклоняются.
- При отключении канала остаётся последний ответ; изменение блокируется.
  Неотправленный текст и черновик формы сохраняются в текущем UI. Обновление
  документа извне не затирает черновик; конфликт требует явного обновления.
- После своего подтверждённого изменения renderer сохраняет несвязанные
  черновики, если их исходные значения не изменились. Черновики не обещаны
  переживать перезагрузку вкладки.
- Публикации хранятся в существующем snapshot канала: максимум 64 источника,
  8 документов, 64 intent и 8 снимков поверхностей; журнал ограничен 200
  сообщениями. Это ограниченная история представления, не новая база конфигурации.
- `surface_id` отделяет вкладки интерфейса, но не является авторизационным
  секретом. Доступ к HTTP-каналу остаётся в существующей operator boundary;
  MCP использует текущую привязку агента и scopes конкретного credential.

## Интерфейс и голос

Сохранены Pearl-материалы, движение объектов, камера, фокус и жесты.
Документ расположен перед агентом, сворачивается без потери текущего черновика
и не создаёт боковую панель. На телефоне текстовые поля и select занимают
полную ширину; числа и переключатели сохраняют компактные строки.

Распознавание речи остаётся браузерным и передаёт текст в тот же agent-channel.
Для микрофона необходимы поддерживаемый браузер, разрешение пользователя и
secure context. Автоматическое воспроизведение и вызовы TTS из Pearl UI
удалены. Существующий серверный TTS endpoint и модель не удаляются и не
перенастраиваются этим изменением.

## Проверка и запуск

Серверные сценарии: `tests/test_agent_interface.py` — реальные MCP handlers и
canonical Endpoint services с изолированной тестовой нодой; HTTP transport,
credential-scoped remote MCP, stale/duplicate/readonly/type защиты и persistence.
`tests/test_codex_agent_bridge.py` проверяет существующий bridge.

Из корня репозитория:

```powershell
.venv/Scripts/python.exe -m pytest -q -o addopts='' tests/test_agent_interface.py tests/test_mcp_server.py tests/test_mcp_remote.py tests/test_codex_agent_bridge.py
```

Из `web/operator-dashboard`:

```text
pnpm exec vitest run tests/unit/spatial-agent-document.test.tsx
pnpm exec playwright test tests/e2e/spatial-agent-document.spec.ts --project=chromium
pnpm build
```

Playwright проверяет desktop/mobile, доступность frame/composer, точный diff,
подтверждённое обновление и отсутствие прямых конфигурационных/TTS-запросов.
Его данные явно синтетические: тест браузера не является доказательством
работы LLM или конфигурации ноды 122. Существующий тест
`test_mcp_steward_action_guard_is_causal_and_claim_only` воспроизводит отказ
также на исходном коде HEAD и требует отдельного разбора.

Локальная production-сборка не публикует страницу на ноду. Для выкладки нужно
обновить backend, bridge и frontend вместе, собрать packaged assets только
через `tools/build-operator-dashboard.sh`, сохранить runtime data/credentials
и перезапустить соответствующие сервисы после согласования. Не редактировать
`src/aidn_hypervisor/static/react-dashboard` вручную.

После согласованной выкладки: открыть прежний HTTPS URL Pearl, попросить
«Покажи настройки endpoint …», сверить readonly/редактируемые поля с нодой.
Проверять запись только на явно выбранном тестовом endpoint; не менять рабочие
параметры ради smoke-теста. Отдельно проверить отказ при недостаточных правах
и сохранение черновика при конфликте.
